### **1\.3 RunPluginServiceImpl\.java 复合插件**

**文件**: `.../module/application/service/RunPluginServiceImpl.java` **行数**: 298 行 **注解**: `@NodeType(FlowNodeTypeEnum.PLUGIN_MODULE)` **核心设计**: ★ 插件即子 Workflow ★

```Java
@Service
@NodeType(FlowNodeTypeEnum.PLUGIN_MODULE)
public class RunPluginServiceImpl implements ModuleService {

    @Autowired
    private WorkFlowEngine workFlowEngine;  // ← 核心: 复用同一个引擎

    @Override
    public Map<String, Object> execute(DispatchData dispatchData) {
        // ===== 1) 加载插件定义 =====
        String pluginId = params.get("pluginId");
        // ★ 区分个人/社区来源 ★
        SplitCombinePlugin split = authPluginCanUse(pluginId, teamId, dispatchData);
        // pluginId 格式: "COMMUNITY-pluginId" 或 "pluginId"(个人)
        //     → splitCombinePluginId() 按 "-" split 解析

        // ===== 2) 获取插件运行时定义 =====
        RuntimePlugin plugin = getPluginRuntimeById(pluginId, split, dispatchData);
        // 社区插件: CommunityPluginManager.getCommunityPlugin()
        // 个人插件: PluginStoreService.getOne(pluginId)

        // ===== 3) ★ 插件节点 → ModuleItemType 列表 ★ =====
        List<ModuleItemType> modules = transModules(plugin);
        // 插件内部可能有多个节点:
        //   [pluginInput, pluginHttp, pluginPython, pluginOutput]
        // 这些节点同样会被 WorkFlowEngine 执行

        // ===== 4) 找到插件入口 ★ =====
        ModuleItemType inputModule = modules.stream()
            .filter(item -> item.getFlowType().equals(PLUGIN_INPUT))
            .findFirst().orElse(null);

        // ===== 5) 为入口注入参数 ★ =====
        Map<String, Object> startParams = buildParams(hasDynamicInput, inputModule, params);
        // 固定参数 + 动态参数 (DYNAMIC_INPUT_KEY)

        // ===== 6) ★ 嵌套调用 WorkFlowEngine ★ =====
        ChatDispatchParam chatDispatchParam = new ChatDispatchParam();
        BeanUtils.copyProperties(dispatchData, chatDispatchParam);
        chatDispatchParam.setModules(modules);        // 插件的节点列表
        chatDispatchParam.setStartParams(startParams); // 插件入口参数

        FlowContext flowContext = workFlowEngine.dispatchModules(chatDispatchParam);
        // ↑ 插件内部走完整的 DAG 执行引擎!

        // ===== 7) 收集输出 =====
        return buildResponse(dispatchData, plugin, flowContext);
    }
}
```

**面试要点**: 插件不是简单函数调用，而是一个**递归的 WorkFlow 实例**。这意味着：

- 插件内部可以包含任意节点 \(LLM/检索/条件分支/循环\)

- 插件可以嵌套另一个插件 → WorkFlowEngine\.dispatchModules\(\) 递归

- 递归深度由 DAG 结构自然限制，不需要显式递归保护

### **1\.4 PluginHttpServiceImpl\.java HTTP 插件**

**文件**: `.../module/application/service/PluginHttpServiceImpl.java` **行数**: 302 行 **注解**: `@NodeType(FLOW_NODE_TYPE_ENUM.PLUGIN_HTTP)`

```Java
@Service
@NodeType(FlowNodeTypeEnum.PLUGIN_HTTP)
public class PluginHttpServiceImpl implements ModuleService {

    @Override
    public Map<String, Object> execute(DispatchData dispatchData) {
        // 1) 构建请求参数 → HttpRequestProps
        HttpRequestProps requestProps = buildProps(dispatchData);
        // 从 input 提取:
        //   system_httpReqUrl, system_httpMethod, system_httpHeader,
        //   system_httpParams, system_httpJsonBody, timeout, retry,
        //   defaultJsonResult, hasHttpAuth, httpAuthType,
        //   httpAuthKey, httpAuthValue

        // 2) ★ 变量替换 ★
        Map<String, Object> concatVariables = new HashMap<>();
        concatVariables.putAll(dispatchData.getVariables());
        concatVariables.putAll(dispatchData.getParams());  // 节点自己的 params
        parseHeader(requestProps, concatVariables);
        parseParams(requestProps, concatVariables);
        parseReqUrl(requestProps, concatVariables);        // URL 中的 {{host}} → 实际值
        parseRequestBody(requestProps, concatVariables);   // JSON body 中的 {{userId}} → 实际值

        // 3) ★ 认证 ★
        addAuth(request, requestProps);
        // Bearer: request.bearerAuth(httpAuthValue)
        // Basic: request.basicAuth(httpAuthKey, httpAuthValue)

        // 4) ★ 重试执行 ★
        int maxRetryTimes = requestProps.getRetry() != null ? requestProps.getRetry() : 1;
        for (int i = 0; i < maxRetryTimes; i++) {
            HttpResponse response = request.execute();
            if (response.isOk()) {
                // ★ JSON 扁平化解析 ★
                JSONObject resJson = JSONObject.parseObject(response.body());
                parseJson(formatResponse, resJson, "");
                //  {"user":{"name":"张三"}} → {"user.name":"张三"}
                success = true;
                break;
            }
        }

        // 5) ★ 失败兜底 ★
        if (!success) {
            if (isNotEmpty(requestProps.getDefaultJsonResult())) {
                parseJson(formatResponse, JSONObject.parseObject(defaultJsonResult), "");
            } else {
                throw new FlowBusinessException(msg, response);
            }
        }
        return output;
    }
}
```

**关键能力**:

- URL/Header/Body 的 `{{variable}}` 模板变量替换

- Bearer/Basic 认证自动注入

- JSON 嵌套扁平化为 `key.subkey` 格式供下游节点引用

- 超时 \+ 重试 \+ 兜底 JSON 三层容错

### **1\.6 AutoAgentToolContext\.java 工具分发器**

```Java
@Component
public class AutoAgentToolContext {
    // ★ Spring 自动注入所有 AutoAgentToolBaseTool 实现 ★
    private final List<AutoAgentToolBaseTool> toolSchemaList;

    // toolRun: 执行工具 (被 Python Agent 通过 /api/v1/tools/run 调用)
    public String toolRun(ToolCallDTO toolCallDTO) {
        String type = toolCallDTO.getType();  // "plugin" / "mcp" / "workflow" / "autoAgent" / "dataset"
        AutoAgentToolBaseTool converter = findConverter(type);
        return converter.callTool(toolCallDTO);  // ★ 各工具各自实现 callTool
    }

    // convert: 工具 Schema 转换 (将 ToolOriginalDTO → FunctionDeclaration)
    public JsonSerializable convert(ToolOriginalDTO toolOriginalDTO) {
        AutoAgentToolBaseTool converter = findConverter(toolOriginalDTO.getType());
        converter.validate(toolOriginalDTO);
        return converter.tryInto(toolOriginalDTO);
    }

    // ★ 工厂模式: 找到支持的转换器 ★
    private AutoAgentToolBaseTool findConverter(String type) {
        return toolSchemaList.stream()
            .filter(converter -> converter.supports(type))
            .findFirst()
            .orElseThrow(() -> UNSUPPORTED_TOOL);
    }
}
```

```Python
def fill_custom_metadata(self, event, idx):
    if event.content and event.content.parts:
        for part in event.content.parts:
            if part.function_response:
                result = part.function_response.response.get("result")
                # ★ 从工具返回中提取文件信息 ★
                result = json.loads(result)
                if isinstance(result, dict):
                    if file_infos := result.pop("fileInfos", None):
                        event.custom_metadata["fileInfos"] = file_infos
                # 去掉 result 中的 fileInfos (不重复序列化)
                part.function_response.response["result"] = json.dumps(result)

# 前端收到 SSE Event:
# event: plugin
# data: {..., "custom_metadata": {"fileInfos": [
#   {"fileName":"架构图.png", "fileUrl":"https://s3.../xxx.png"}
# ]}}
# → 前端直接渲染 <img src="..." /> 或 <video src="..." />
```

### **插件/工具模块**

#### **Q1: 插件和 Dify 的 Tool 有什么区别？**

**核心差异: AgentFlow 的插件是完整的子 Workflow，Dify 的 Tool 是单一 Python 函数。**

```Plain Text
Dify Tool:    用户输入 → tool_function() → 返回结果  (一步)
AgentFlow 插件: 用户输入 → pluginInput → pluginHttp → pluginPython → pluginOutput (完整 DAG)
                          └── 内部递归调用 WorkFlowEngine ──┘
```

**实现原理**: `RunPluginServiceImpl.execute()` 加载插件的节点列表（JSON → `ModuleItemType` 列表）→ 找到入口节点 `pluginInput` → 注入参数 → 调用 `WorkFlowEngine.dispatchModules()` 递归执行。插件内部可以有任意节点组合——LLM 对话、知识库检索、条件分支、循环、HTTP——甚至可以再嵌套另一个插件。

#### **Q2: 五种工具类型的执行链路各有什么不同？**

**统一入口**: 所有类型都通过 `POST /api/v1/tools/run` → `AutoAgentToolContext.toolRun()` → `findConverter(type)` 自动分发。新增工具类型只需实现 `AutoAgentToolBaseTool` 接口（`supports(type)` \+ `callTool()` \+ `tryInto()`），无需改网关代码。

#### **Q3: 工具 Schema 怎么自动生成让 LLM 理解的？**

**全链路自动转换**:

```Plain Text
    ↓

Python CommonTool._get_declaration()
```

### **MCP 集成模块**

#### **Q4: MCP 和 Plugin 什么时候选哪个？**

**MCP 协议通信**: JSON\-RPC over SSE（服务端推送）或 stdio（子进程）。连接 MCP Server 后先 `tools/list` 获取工具列表 → 注册为 ADK FunctionDeclaration → LLM 调用时 `tools/call` 传递参数。

#### **Q5: MCP 工具如何注册到 Agent？**

**四步**:

1. 用户在前端注册 MCP Server URL → 写入 `McpServer` 表

2. 为 AutoAgent 配置 `mcpInfoList`（勾选需要的 MCP 工具）

3. Agent 发布时 → `agentMeta.tools.mcpInfoList` 随 JSON 传给 Python

4. Python ADKExecutor 启动时遍历 `mcpInfoList` → 为每个 MCP 工具创建 `CommonTool(tool_type="mcp")` → 注册到 ADK LlmAgent

**工具 ID 格式**: `{mcpServerId}__{toolName}` 双下划线分隔，用于关联 MCP Server 和具体 Tool。

### **记忆模块**

#### **Q6: 为什么长期记忆选 Mem0 向量检索而不是 LLM 结构化摘要？**

**AgentFlow 的选择**: Mem0 向量化记忆。用户偏好以自由文本形式存储，检索时用语义匹配。

**优势**: 灵活——不需要预设话题类别，任何用户偏好都可以存储和检索。语义匹配能关联相关但不完全相同的记忆（"电池"和"续航"语义相近）。

**代价**: 多了一套 Milvus 向量库依赖。语义检索可能返回"语义相关但事实过时"的记忆（用户上个月偏好 5000mAh，这个月偏好变了但旧记忆仍被检索到）。

**如果重做，应该用 LLM 渐进式摘要**: 写 Prompt 约束"只记话题\+状态\+约束，绝对禁止记录具体答案"。优点：不需要向量库、摘要存 MySQL 按 conversation\_id 直接读、不依赖语义检索质量。缺点：不够灵活（无法跨会话关联相似话题）。

#### **Q7: 短期记忆和长期记忆怎么协同？**

```Plain Text
每次对话请求:
1. Redis Session 加载当前 chatId 的完整对话历史（短期记忆，按 historyRound 保留最近 N 轮）
2. Mem0 语义检索与当前问题相关的长期记忆（向量匹配，取 TopK）
3. Prompt 组装顺序:
   System: [Agent 角色定义]
          [长期记忆] "用户偏好电池续航>5000mAh, 预算<4000元" ← Mem0 检索结果
          [对话历史摘要] "之前讨论了产品A和产品B的参数对比" ← Token 超限时 LLM 压缩生成
          [工具声明] function_call 列表
          [背景知识] RAG 检索结果
   User:  当前用户问题
```

### **多模态模块**

#### **Q8: 视频理解的全链路怎么做的？**

```Plain Text
用户上传视频
  → fileSwitch 判断 MIME type="video/*"
    → videoKeyframesExtract 视频抽帧
      → 调用 af-rag-server: POST /rag_algorithm/extract_frame
      → 每 N 秒抽一帧，返回帧图片列表
        → imgCompletion 逐帧理解
          → 调用多模态 LLM (GPT-4V / Claude Vision)
          → "第1帧: 产品参数表格, 第2帧: 电池容量5000mAh..."
            → chatNode 综合所有帧的理解结果
              → LLM: "根据视频内容，产品电池容量为5000mAh..."
```

**与纯文本 RAG 的区别**: 视频理解是多步链式处理——先抽帧再逐帧理解再综合。不是单一 LLM 调用，而是一个小 Workflow。

#### **Q9: AI 生成的多模态文件怎么返回给前端？**

**fileInfos 透传链路**:

```Plain Text
imageGenerate 节点执行
  → 调用 DALL-E / Stable Diffusion API
  → 返回 {fileInfos: [{fileName: "架构图.png", fileUrl: "https://s3.../xxx.png"}],
            answer: "已为您生成以下文件：架构图.png"}

Python ADKExecutor.fill_custom_metadata():
  → 从工具返回的 result JSON 中提取 fileInfos
  → 设置 event.custom_metadata["fileInfos"] = fileInfos
  → 从 result 中移除 fileInfos（不重复序列化）

SSE 推送: event: plugin
          data: {..., "custom_metadata": {"fileInfos": [...]}}

前端渲染: 根据文件类型渲染 <img> / <video> / <audio>
```

**与纯文本回复的区别**: 纯文本回复通过 `answerText` 字段 → SSE ANSWER 事件推送。多模态文件通过 `fileInfos` 字段 → SSE plugin 事件（带 `custom_metadata`）推送。前端根据事件类型区分渲染方式。
