## **公司项目 \(PA/PowerAgent\) —— AI Agent 工作流编排平台**

### **可视化 DAG 工作流编排引擎**

**技术路线**: 自研引擎，非基于 Dify/LangGraph。纯 Java 实现，不依赖外部编排框架。

**DAG 怎么做的**:

**五阶段执行流程**:

```Plain Text
阶段① 节点加载与过滤 (loadModules)
  前端 JSON → 过滤非执行节点（userGuide引导/noteNode便签）→ 处理每个节点的 Input/Output
  ├── Input 处理: 只保留三种 input（system_input系统参数 / connected已连线 / 有默认值）
  └── ★ 变量占位符替换: {{variable}} → FlowContext 中的实际值（MessageFormatUtils.replaceVariable）

阶段② 构建运行时上下文 (FlowContextBuilder)
  同步模式: new FlowContextBuilder().build(runningModules)
    → 创建 switchMap（条件分支结果存储）
    → 加载节点到 moduleItemTypeMap（moduleId → 节点实例，O(1) 查下游）
  并发模式: new FlowContextBuilder().buildExecutor(runningModules)
    → 额外创建 ExecutorService + CompletionService

阶段③ 全局变量注入 (dealGlobalVariable / dealSessionVariable)
  global- 前缀: 本次执行内跨节点透传（如 "global-user_info"）
  session- 前缀: 跨对话持久化（如 "session-customer_level"）

阶段④ 入口节点识别 (initRunningModuleType)
  自动筛选四类入口节点: questionInput / historyNode / pluginInput / loopStart
  为入口节点注入 startParams 初始参数

阶段⑤ 执行模式分发 (dispatchModules)
  concurrency != 1 → 同步递归（checkModulesCanRunSync）
  concurrency == 1 → 线程池并发（checkModulesCanRun）
```

**同步递归模式详解**:

```Plain Text
checkModulesCanRunSync([入口节点])
  for each node in 当前批次:
    ① moduleCanRun(node): 检查所有 input 是否都有值（非 null）
       → 有值为 null → 跳过，等前置节点传数据
    ② moduleInput(node, switchMap): 注入条件分支变量
    ③ SSEUtils.pubMsg(moduleStatus, {status: 1}) —— 通知前端"运行中"
    ④ ★ moduleRun(node) ★:
        ModuleFactory.getService(nodeType) → O(1) 查表获取执行器
        transParam(inputs) → input 列表转为 key-value Map
        moduleService.executeWithTimeout(dispatchData)
          → 若配置了 maxRuntime:
              循环最多 3 次:
                Future.get(maxRuntime, SECONDS) 超时等待
                超时 → future.cancel(false) → 下一轮重试
              全部失败 → 返回 moduleDefaultOutput 兜底值
          → 未配置: 直接 execute()
    ⑤ chatResponseBuild(): 收集节点执行详情（耗时/token/模型名）
    ⑥ SSEUtils.pubMsg(moduleStatus, {status: 2, details}) —— 通知前端"完成"
    ⑦ ★ moduleOutput(node, response, ctx) ★ 找下游:
        pushStore(): 累积 answerText 到最终回复
        遍历 outputItem:
          - globalKey 非空 → 写入全局变量池（跨节点透传）
          - edges 非空 → 通过 moduleItemTypeMap 找到目标节点 → 加入 nextNodes
          - targets 非空 → 精确赋值目标节点的特定 input（outputValue.put(target.key, outputItem.value)）
        → 返回 nextNodes 列表
    ⑧ checkModulesCanRunSync(nextNodes) ← ★ 递归 ★
```

**并发模式详解**:

```Plain Text
checkModulesCanRun([同级节点])
  CountDownLatch latch = new CountDownLatch(nodes.size())
  for each node:
    if moduleCanRun(node):
      completionService.submit(() → {
        try { return moduleRun(node) }
        finally { latch.countDown() }  ← ★ 异常也计数，防死锁 ★
      })
    else:
      latch.countDown()  ← 不满足条件的也计

  latch.await()  ← ★ 等待所有并行任务完成 ★

  for i in 1..执行成功的节点数:
    completionService.take().get()  ← ★ 按完成顺序取，非提交顺序 ★
    → moduleOutput 找下游
    → checkModulesCanRun(下游)  ← ★ 递归下一级并行 ★
```

**为什么节点间数据不会乱？**

依赖检查保证执行顺序——不是显式排序，而是数据依赖驱动。每个节点执行前 `moduleCanRun()` 检查所有 input 是否有值。只有前置节点执行完 → `moduleOutput()` 通过 targets/edges 给下游 input 赋值 → 下游 `moduleCanRun()` 才返回 true。数据流就是拓扑约束。

**节点三种连接方式**:

**outputConnect 模式**（图纸上的"路由节点"）: 所有 output 共享同一组 edges，减少连线数量。普通模式: 每个 output 独立 edges/targets —— 不同输出可以连到不同下游。

**节点注册——工厂\+注解，零配置扩展**:

Spring 启动后触发 `ApplicationReadyEvent` → ModuleFactory 扫描容器中所有 `ModuleService` 接口的实现 Bean → 读取每个实现类的 `@NodeType` 注解 → 注入 `Map<FlowNodeTypeEnum, ModuleService>`。运行时 `getService(type)` 直接查表，O\(1\) 获取执行器。新增节点三步: 实现 ModuleService 接口 → 加 @NodeType 注解 → 在 FlowNodeTypeEnum 加一行枚举值。引擎代码零修改。

**循环节点怎么实现**:

```Plain Text
LOOP_START → LOOP_NODE → LOOP_BREAK
                │
                └── 循环体内的节点链

LOOP_BREAK 节点执行后:
  → 设置 flowContext.loopEndCondition = "true/false"
  → moduleOutput() 中检测到 LOOP_BREAK 类型 → 返回空列表（不找下游，递归终止）
  → 循环控制由 WorkFlow 的 LOOP_START→LOOP_NODE→...→LOOP_BREAK 三节点组合完成
  → LOOP_BREAK 根据条件决定是否跳回 LOOP_NODE 或继续执行后续节点
```

**异常处理和 SSE 实时推送**:

- 业务异常（FlowBusinessException）: 捕获 → 写入 errorMessage \+ chatResponse → SSE 推送 status=3（异常）\+ 错误详情 → 不中断后续独立节点

- 系统异常（Exception）: 捕获 → 写入兜底错误信息 `"系统错误: {message}"` → SSE 推送 status=3 → 不中断

- 异常信息的 ChatHistoryItemResType 带 moduleId/moduleName/moduleType，前端可定位到具体节点

**分支判断怎么实现**:

- 条件节点 `tfSwitch`：配置多条判断规则（如 `{{quoteQA.length}} > 0`），运行时用 QLExpress 规则引擎解析变量表达式，逐条求值，命中的规则通过 edges 连接激活对应下游分支

- 检索结果分支：`datasetSearchNode` 执行后输出 `isEmpty` / `unEmpty` 两个布尔值 → 下游 `tfSwitch` 根据这两个值路由。有结果走 `chatNode`（LLM 回答），空结果走兜底分支（自定义回复/人工转接）

- 文件类型分支：`fileSwitch` 判断用户上传文件的 MIME 类型，路由到不同多模态处理节点（image/\* → 图像理解、video/\* → 视频抽帧、audio/\* → 语音识别）

**信息不全怎么处理**:

- 节点级：每个节点执行前检查 `moduleCanRun()`——所有 input 是否都有值。input 为空的不执行，等前置节点通过 edges/targets 把数据传过来后再激活

- 对话级：LLM 缺少关键信息时，通过 PlanReAct 的 REASONING 阶段自主判断——能在上下文找到的信息自动补齐，找不到的向用户追问

- 检索级：知识库检索无结果时走三级兜底——用户配置的自定义回答 → 工作流空结果分支 → LLM 自主换关键词重试

- 执行级：单节点超时/失败后自动重试（最多 3 次），全部失败返回 `moduleDefaultOutput` 兜底值，不中断后续节点的执行

### **多 Agent 自主推理与协作**

**技术路线**: 基于 Google ADK（Agent Development Kit），非 LangChain/LangGraph。投入生产前评估了 LangGraph 的 StateGraph 方案，最终选 ADK 因为其原生支持层次化 Agent 树和 PlanReAct 规划器，开发效率更高。同时保留 LangGraph 作为备用框架（`framework` 参数热切换）。

**Agent 循环怎么做的**:

- 基于 ADK 内置 PlanReActPlanner，定制 `CustomPlanner` 控制 LLM 输出格式——PLANNING（制定计划）→ ACTION（工具调用）→ REASONING（中间推理）→ FINAL\_ANSWER（最终答案）四阶段循环。每轮 LLM 调用生成一个新的 Event，ADK Runner 按 `max_llm_calls=20` 控制循环上限

- 定制 Plannner 实现信息分级：PLANNING 阶段展示给用户作为"思考过程"，ACTION（工具调用参数）和 REASONING（中间推理数据）隐藏，兼顾透明度和安全性

- 失败后 `/*REPLANNING*/` 机制让 LLM 从执行结果中学习并重新规划，而非简单重试同一策略

- 死循环三层防御：`max_llm_calls=20` 硬上限阻断 / 发布前 DFS 检测阻止 Agent 嵌套环 / 单节点 `Future.get(maxRuntime)` 超时保护

**多 Agent 怎么路由**:

- 层次化 Agent 树：IntentAgent（根节点，负责意图判定和任务分发）→ 5 个专业子 Agent（strategyAgent 策略分析 / metadataAgent 元数据框架 / directAnalysisAgent 用户数据分析 / strategyViewAgent 策略查看 / runDataAgent 数据运行）。每个子 Agent 独立配置工具集和知识库，State 字典跨 Agent 透传

- IntentAgent 两层路由：`before_agent_callback` 显式分支——代码判断确定性场景（检查策略发布状态等），命中后直接返回结果跳过 LLM；Prompt 驱动路由——模糊场景用 `transfer_to_agent(X)` 指令分发，"只能分发不能回答"写死在 Prompt 里

**上下文怎么组装**:

- 每次 LLM 调用前，`before_model_callback` 裁剪对话历史——按 user 消息为分界线，只保留最近 N 轮（`historyRound` 配置），丢弃旧轮次

- Prompt 七段拼接：Agent 角色定义 → 工具 FunctionDeclaration 声明 → PlanReAct 执行指令 → 长期记忆（Mem0 语义检索结果）→ RAG 背景知识（搜索到的文档 chunk）→ 引用溯源格式要求 → 多模态能力兜底文案

- 工具调用后，LLM 返回的 `function_call` → `CommonTool.run_async()` → HTTP 调用 Java 端 `/api/v1/tools/run` → 返回 `function_response` 注入 LLM 下一轮上下文

### **混合 RAG 检索引擎**

**技术路线**: 自研检索引擎，存储层基于 ES 8\.x（非 Milvus 为主要向量库——因为 ES 8\.x 原生支持 KNN 且无需额外部署向量数据库）。Embedding 调用外部模型 API（text\-embedding\-3\-large, 768 维）。

**检索怎么做的**:

- 三模式可切换：`EMBEDDING`（ES KNN 向量检索）→ 适合语义模糊查询；`FULLTEXT_RECALL`（ES BM25 全文检索）→ 适合精确关键词匹配（订单号、错误码）；`MIXED_RECALL`（两路并行→RRF 融合→Rerank 精排）→ 默认模式，兼顾语义理解和精确匹配

- 混合召回时同时调用 ES KNN 和 ES Bool Query，向量权重 0\.6、全文权重 0\.4，分别按比例分配 recallLimit。两路结果通过 RRF（Reciprocal Rank Fusion）融合——对排名而非原始分数加权，解决 BM25 和 Cosine 分数量纲不可比的问题

- bi\-encoder 粗召回 \+ cross\-encoder 精排两阶段：ES KNN 从全量候选取 TopK（bi\-encoder），PEG Ranker 对缩减后的 \~50 条做 query\+doc 联合编码重排序（cross\-encoder），过滤 similarity 阈值以下的低分结果

- 权限三层过滤：知识库级权限 → 数据集启用/禁用 → ES 查询时 `isEnabled` 字段排除

**信息不全/召回不到怎么处理**:

- 多知识库检索时自动校验类型一致性和向量模型一致性（不同模型维度不同，混合检索分数偏差），不一致的知识库被静默排除

- 检索结果为空时：用户预设的自定义兜底回答 → 工作流节点输出 `isEmpty=true`，下游 `tfSwitch` 路由到兜底回复分支 → LLM 在 PlanReAct 循环中自主判断，换关键词重试或告知用户"未找到"

### **工具调用网关 \& Agent 生命周期**

**工具统一网关怎么做的**:

- 单一入口 `/api/v1/tools/run` ，接收 `{id, name, type, params}` → `AutoAgentToolContext` 根据 `type` 字段自动分发到对应执行器。5 种工具类型（plugin 内部插件 / mcp MCP 外部服务 / workflow 子工作流 / autoAgent 嵌套 Agent / dataset 知识库检索）各自实现 `supports(type)` 和 `callTool()`

- Python 端 `CommonTool.run_async()` 封装 HTTP 调用，`KnowledgeTool` 封装知识库检索参数（searchMode/recallLimit/similarity），工具调用后 `after_tool_call` 钩子自动记录知识库引用用于最终溯源

- 工具 Schema 全链路自动转换：前端配置 → Java 端 `tryInto()` 生成 `FunctionDeclaration` → Python ADK 注册为 `BaseTool` → LLM 通过 `function_call` 调用。新增工具只需实现接口 \+ `@Component` 注解，注册表自动发现

**Agent 生命周期管理**:

- 快照版本管理：每次发布生成不可变快照，字段级快照（tools/knowledge/modelInfo 等 6 个 JSON 字段存储在 MySQL），支持版本回溯和 A/B 测试

- 草稿模式：`draftMode=true` 全链路透传至工具调用层，执行时自动跳过真实支付/消息推送/数据修改

- 发布前校验：DFS 循环检测阻止 Agent 嵌套环 \+ 知识库全局配置完整性校验（backupStrategy/showSource/retrieveMaxLength 不可为空）

### **上下文管理与双层记忆**

**Token 超长怎么处理**:

- 快速路径：文本总字符数 \< maxTokens × 0\.5 时跳过计算直接放行

- 精确截断：JTokkit（Tiktoken 的 Java 平替）逐条计算 token 数，从后往前累加至上限后截断，Human\+AI 成对移除保证对话结构完整

- LLM 摘要压缩：开摘要开关时，不从后往前截断，而是调 LLM 将完整历史压缩为语义摘要（"用户咨询了产品A电池参数，已告知5000mAh"），摘要替换原始历史，大幅减少 token 消耗。摘要存 ChatItem 表，下次读取直接复用

- 摘要后仍超限 → 直接抛异常，拒绝继续，避免 LLM 收到截断混乱的上下文

**长短期记忆**:

- 短期记忆：Redis Session 按 chatId 存储完整 Event 列表，每次请求恢复会话，按 `historyRound` 保留最近 N 轮

- 长期记忆：Mem0 向量化引擎，用户偏好以自由文本形式向量化存储到 Milvus，检索时语义匹配注入 Prompt 的 `【长期记忆】` 段

- 记忆字段支持团队级自定义配置（`TeamMemoryFieldConfig` 表），不同 Agent 可选择性开启（`AgentMemoryFieldRelation` 表），避免无关记忆干扰推理。会话变量通过节点写入全局变量池（前缀 `session-`）跨对话持久化

### **工程架构**

**双引擎怎么分工**:

- WorkFlow 引擎：处理实时对话（毫秒级响应），JVM 内存内执行（无序列化开销），单节点超时\+重试\+默认值兜底。适合 50 节点以内的对话级 Workflow

- DataFlow 引擎：处理知识库 ETL 跑批（分钟级延迟），DB 驱动分段调度（Job 每 30s 轮询 MySQL 取待执行 Context），双层状态机（Context 层 INIT→TRANS→SUCCESS/FAILURE \+ Node 层 INIT→PROCESS→SUCCESS/FAILURE），失败指数退避重试（2^n × 60s，最多 3 次）

- 文档处理时大小文件分流：\< 200MB 直接 JVM 内存执行，≥ 200MB 提交 Argo K8s Pod 执行，避免大文件 OOM 阻塞在线服务

- 两个引擎通过 MySQL 共享表（knowledge\_flow\_context 表）异步协作——Agent 端创建 Context 记录 → DataFlow 轮询取到 → 执行完成更新状态。无需消息队列中间件

**跨语言怎么协作**:

- Java（agentflow\-server 编排 \+ dataflow\-server ETL）\+ Python（af\-rag\-server AI 能力）。DataFlow 需要文档解析/分块/摘要时 HTTP 调用 Python（`POST /rag_algorithm/parser` 等），Python Agent 需要执行工具时 HTTP 调用 Java（`POST /api/v1/tools/run`）

- 可观测性统一：Pinpoint 全链路追踪跨语言透传 traceId \+ Langfuse 记录每次 LLM 调用和工具调用的完整 span \+ Prometheus 暴露指标

- 高频操作（Embedding）已直接从 Java 调用模型 API，不经过 Python 中间层

## **个人项目 \(Ragent\) —— 深耕 RAG 检索增强全链路优化**

在公司项目中构建了 Agent 平台的整体能力后，个人项目聚焦 RAG 方向的深度优化——文档切分、意图路由、检索排序、记忆系统。以下按"问题→技术路线→实现细节"展开：

### **结构感知文档切分**

**技术路线**: 自研 Block 体系 \+ 多策略切分器，非直接使用 LangChain RecursiveCharacterTextSplitter。底层解析用 MinerU（PDF→强类型 Block），切分逻辑自研。

### **细粒度意图树与 Query Rewrite**

**技术路线**: 意图分类用 LLM 而非 TinyBERT——20\+ 叶子节点的细粒度分类超出了 BERT 的语义理解能力。Query Rewrite 两级处理（规则\+LLM），失败的降级路径保证可用性。

### **多路检索与后处理器链**

**技术路线**: 四通道并行 \+ 四步后处理器链（责任链模式）。模型调用三态熔断保护，Rerank noop 兜底保证故障不影响主流程。

### **渐进式 LLM 长期记忆**

**技术路线**: 选择了 LLM 结构化摘要而非 Mem0 向量检索。决策原因：摘要只记话题不记答案——RAG 实时检索最新文档，摘要里的旧答案会和文档冲突。

**技术路线**: 自研 Block 体系 \+ 多策略切分器，非直接使用 LangChain RecursiveCharacterTextSplitter。底层解析用 MinerU（PDF→强类型 Block），切分逻辑自研。

**切分怎么做的**:

- Block 体系：PDF 经 MinerU 解析产出强类型 Block——HEADING（标题）/ TABLE（表格）/ CODE（代码块）/ ATOMIC（图片/公式等不可拆单元）/ PARA（段落）/ LIST（列表）。每个 Block 自带类型标记和相关元数据（页码、层级路径 outlinePath）

- 两套切分策略可切换：FIXED\_SIZE 固定长度切分（chunkSize=512, overlap=128，优先在换行符边界对齐，URL 断行自动修复）\+ STRUCTURE\_AWARE 结构感知切分（按 Block 边界累积至 target=1400 字符，标题/代码/图片不会从中间切开）

- 表格专用切分器 TableChunker：200 行 Excel → 贪心按行累加体量预算（maxChars=1800, rowsPerChunk=50），超出触发切块。单行超预算时自成一块不拆散

- **表格 key\-value 语义化渲染**（核心创新）：将 markdown 表格 `| 研发部 | 500万 | 2024 |` 转为 `部门: 研发部; 预算金额: 500万; 年度: 2024`。把列名\-值的对应关系写进字面文本，Embedding 模型能直接编码列名值关系而非靠位置推断。原理：bi\-encoder 对整个序列做加权平均，markdown 表格的位置信号被稀释；key\-value 中 `部门: 研发部` 被模型作为一个完整语义单元编码

- chunk 双文本设计：`content` 存 markdown 表格（LLM 可读），`embeddingText` 存 key\-value 格式（Embedding 专用）。每个表格 chunk 带 `sectionContext`（sheet 名 \+ 所有列名），方便 LLM 感知"这是某个表的片段"

- ChunkPacker 打包：各切分器只负责"单个 Block 内切分"，天然"只拆不并"。ChunkPacker 贪心合并碎片到 chunkSize 预算（如"平台介绍"20字符 \+ "\- 多路检索"5字符 \+ "\- 意图识别"5字符 → 合并为一块），TABLE/CODE 类型标记为不可合并保护结构完整性。块级 overlap 取自缓冲区尾部完整 Block，不硬切

- **"等价父文档"**（创新点）：传统父子文档需存两套 chunk、双倍 Embedding 成本。Ragent 只存一套 chunk，检索命中后回表补齐元数据（docId/chunkIndex/docName）→ 按 docId 分组 → 按 chunkIndex 还原原文顺序 → 渲染上下文 `<content source="员工手册">`，效果等同取父 chunk 全文

### **细粒度意图树与 Query Rewrite**

**意图树怎么做的**:

- 20\+ 叶子节点意图树在管理后台可视化编辑，节点结构：intent\_code（节点编码）/ parent\_code（父节点）/ kind（KB/MCP/SYSTEM 三类）/ collection\_name（目标知识库）/ TopK（检索数量）/ promptSnippet（该意图专属 Prompt 约束片段）/ mcpToolId（关联的 MCP 工具）

- 每个子问题独立并行调 LLM 分类（`intentClassifyExecutor` 线程池），一次性对所有叶子节点打分，score \< 0\.35 的意图丢弃，每子问题最多保留 3 个意图

- KB/MCP/SYSTEM 三路分发：kind=KB 走检索（只搜目标 collection），kind=MCP 走工具调用（携带 mcpToolId），kind=SYSTEM 直接 LLM 闲聊回复不走检索

- 歧义引导机制：多意图 score 接近（分差 \< 0\.05）→ 主动列出选项让用户选择而非猜一个

- 安全网机制：全局最高意图分 \< confidenceThreshold\(0\.6\) → 触发全局检索兜底（全库搜索保证不返回"未找到"）

**Query Rewrite 怎么做的**:

- 两级处理：规则级术语归一化（`QueryTermMappingService` 从 DB 加载映射表 \+ Redis 缓存，"平安保司"→"平安保险公司"，不调 LLM）\+ LLM 改写拆分（调小模型做口语化改写和多问题拆分）

- 改写策略关键约束：专有名词（系统名、产品名）原样保留不得修改 / 礼貌用语删除 / 多问号拆分 / **抽象对比不拆分**——"X和Y有什么区别"拆成两个独立查询后各自检索出两套文档，LLM 无法做对比，因为两份文档没有交叉信息

- 容错设计：LLM 改写失败 → 回退到规则拆分（按 `？！。；\n` 分隔符切 \+ 术语归一化），保证降级路径。配置开关 `rag.query-rewrite.enabled` 控制是否启用 LLM 改写

### **多路检索与后处理器链**

**检索怎么做的**:

- 四通道并行：意图定向通道（命中意图树指定的 collection\_name，精确路由到目标知识库）\+ 关键词 BM25 通道 \+ 语义向量全局通道 \+ 联网搜索通道。`CompletableFuture.supplyAsync()` 并行执行，单通道异常返回空结果不扩散

- RRF k 值深度分析：k=60 默认，rank 0\(1/61=0\.0164\) vs rank 9\(1/70=0\.0143\) 差异 13%；k=20 差异 30% 更相信高名次；k=100 差异 8% 几乎平等看待。可根据通道质量动态调整（某通道压制其他→增大k；噪音多结果分散→减小k）

**后处理器链怎么做的**:

- 四步处理器（责任链模式，`getOrder()` 控制顺序）：去重合并（多通道命中同一 chunk 时按通道优先级保留最高分）→ RRF 排名融合 → Rerank 精排截断（rerankCandidateLimit=50，Cross\-Encoder 只对 50 条做深度语义匹配，先粗筛再精排控制成本）→ 元数据富化（回表补齐 docId/docName/chunkIndex）

- Rerank 模型调用 qwen3\-rerank cross\-encoder：query\+"\[SEP\]"\+doc → 直接输出相关性分数。合并 RRF 之后做——RRF 把 100\+ 候选粗筛到 50 个，Cross\-Encoder 只对这 50 个做深度匹配（Cross\-Encoder 比 Bi\-Encoder 慢 10\-50 倍，全量直接算不可接受）

### **渐进式 LLM 长期记忆**

**技术路线**: 选择了 LLM 结构化摘要而非 Mem0 向量检索。决策原因：摘要只记话题不记答案——"RAG 实时检索最新文档，摘要里的旧答案会和最新文档冲突"，这是纯文本记忆的核心 bug。

**渐进式怎么做的**:

- 触发条件：summaryEnabled=true \+ 角色=ASSISTANT \+ 用户消息数 \>= summaryStartTurns（默认9轮）。每次 assistant 回复后异步检查

- 窗口计算：取最近 keepTurns 条 user 消息作为"保留原文区"，更早的消息进入摘要窗口（afterId 到 summaryCutoffId）。每次只摘要新增消息（非全量），合并旧摘要输出新摘要

- 摘要格式约束：不超过 max\_chars 字符，单行输出，只记话题\+状态\+约束，绝对禁止记录具体答案。格式：`用户咨询了【话题1】（状态）、【话题2】（状态）。约束：约束1。关键词：词1`

- 存储：MySQL t\_conversation\_summary 表，按 conversation\_id 直接读取（不依赖向量检索），加载时 `<conversation-summary>` 标签包裹放在历史消息前面

### **分布式文档同步调度**

**怎么做的**:

- DB 乐观锁调度：`UPDATE ... SET lock_owner=? WHERE id=? AND (lock_until IS NULL OR lock_until < now())`，抢不到说明其他实例在处理。心跳每 lock\_seconds/3 续约一次，lease 丢失 → `shouldAbortForLeaseLoss()` 中止，绑 ID 释放（`WHERE id=? AND lock_owner=?`）只解自己的锁

- 三级变更检测：HTTP HEAD → ETag 未变直接跳过（零下载流量）→ Last\-Modified → SHA\-256 内容哈希。三级命中率递减但可靠性递增

- 事务原子写入：删旧chunk（MySQL）→写新chunk（MySQL）→删旧向量（Milvus）→写新向量（Milvus）→更新文档状态。Spring 事务保证 MySQL 原子性，Milvus 不支持事务——失败后文档状态置为 FAILED，用户手动重试，重试时 filter 条件仍匹配不会残留旧向量
