## Q0：先理清——意图识别的本质 & 两套项目的定位差异

### 一句话定义

> 意图识别 = **"用户说了什么 → 该让哪个处理器去处理"** 的决策。决策对象可以是知识库、工具、子 Agent，还是直接闲聊。它本质是个**路由器（router）**问题，不是检索问题。

要问意图识别答得好，先答三个子问题，业界所有方案都围绕它们打转：

| 决策问题 | 两种落点 |
|---|---|
| 分给谁 | 某类处理器：KB 检索 / 工具 / 子 Agent / 闲聊直接答 |
| 分多细 | **粗粒度**（几个业务场景）vs **细粒度**（几十个叶子意图/知识库） |
| 谁来判 | **确定性规则**（代码/关键词，快且稳）vs **语义判断**（LLM/模型，灵活） |

### 两个项目的"意图"根本不是一回事（这是最重要的认知）

两个项目虽然都叫"意图识别"，但**粒度、载体、下游完全不同**——面试最容易在这里被绕晕，先把画像立住：

| | ragent（Java 单体 RAG） | PowerAgent（Java + Python Agent 平台） |
|---|---|---|
| 要解决的问题 | FAQ 知识问答：**该查哪个知识库/collection** | 多业务 Agent 平台：**该派给哪个子 Agent 干活** |
| 粒度 | **细粒度**（意图树叶子可直接映射到 collection_name） | **粗粒度**（5 个子 Agent 级别的业务场景） |
| 决策对象 | KB 定向检索 / MCP 工具 / SYSTEM 闲聊短路 | transfer_to_agent 到子 Agent / 社交直接回复 |
| 载体 | DB 配置的**三层意图树**（t_intent_node） | IntentAgent 的**代码分支 + Prompt 规则** |
| 识别机制 | LLM **一次性对所有叶子打分** + 阈值分流 | 先**代码显式分支**，模糊场景再 **LLM 路由** |
| 对应业界谱系 | ① + ②（确定性）+ ③（语义兜底）的**混合体**（详见 Q1/Q2） | ①（显式分支）+ ⑤/⑥（LLM 路由/多 Agent 委托）的**混合体**（详见 Q3） |
| 和 Rewrite 关系 | 意图识别是独立管线步，且**在 Query 改写之后** | 无独立 Rewrite，靠 Agent 循环 REASONING 隐式完成 |
| 为什么这么设计 | 专做 FAQ：口语化/术语必须先规范化才能命中细粒度意图 | 做多业务 Agent：意图粗、场景固定，靠子 Agent 深度执行 |

> **先记住这句判断**：ragent 的意图识别本质是**"知识库级的路由"**，PowerAgent 的本质是**"任务分发级的路由"**——粒度不同不是因为谁先进谁落后，而是**场景不同**（FAQ 知识问答 vs 多业务 Agent 平台）。

## Q1：业界成熟方案全景（6 档谱系）

业内没有"标准意图识别模块"，而是一张**从"便宜确定"到"贵但灵活"的谱系**。按决策者分类：

### 档位总览

```
① 无意图识别 ──→ 直接全局检索 / 全局 Agent
② 规则/关键词  ─→ if-else、正则、精确匹配词           【确定性 100%，零成本，不可扩展】
③ 语义路由     ─→ Embedding 相似度 → 最近意图          【快、便宜，边界模糊易误吸】
④ 分类模型/NLU ─→ 微调小模型/Rasa 式 intent 分类       【低延迟稳定，要标注+训练，扩类麻烦】
⑤ LLM 打分分类 ─→ LLM 一次对所有候选打分/输出 label     【灵活，能处理复合，每次多一次 LLM 调用】
⑥ LLM 路由委托 ─→ LLM 决策 + 转发给子 Agent/执行器      【多步执行，能拆任务，有失控/死循环风险】
```

### 逐档详解（含代表产品，答"业界成熟方案"用）

**① 无意图识别——直接全量检索 / 单一 Agent（基线）**
- 代表：朴素 RAG Demo、单知识库单一 Agent 工具。
- 优点：零配置零额外成本；缺点：无法区分 KB/MCP/闲聊、全库噪声大。
- 定位：**单一知识库、无工具时用它，够用别过度设计。**

**② 规则/关键词路由（决策表）**
- 代表：早期任务型 Bot 的手写决策树；PA 的 `before_agent_callback` 显式分支（代码判断"策略是否已发布"）；ragent rewrite 的精确实体短路（正则判"含 4 位以上数字"）。
- 优点：确定性 100%、零 LLM、超低延迟；缺点：口语化/同义词失效、维护成本随规则爆炸。
- 定位：**适合"意图 100% 确定"的窄场景**，放最前当便宜的旁路，而不是当主路由。

**③ 语义路由（Embedding 相似度）**
- 代表：Semantic Router（Aurelio Labs）、LlamaIndex `RouterQueryEngine`、Milvus/pgvector 自建意图向量库。
- 做法：Query embedding 与每个意图/路由描述文本算相似度，取最近。
- 优点：不需要 LLM，便宜快；缺点：**边界模糊的 query 会被"吸"到语义近但错的类**（如"ADK 和 React 区别"两个候选分接近，判不了该归谁）；无法处理复合意图。
- 定位：候选类之间**语义距离足够大**时很好用；类之间近似时不可靠。

**④ 分类模型/NLU（监督学习 intent）**
- 代表：Rasa NLU、经典 Dialogflow/自研意图分类模型（微调 BERT/小型分类头）。
- 做法：离线训练一个多分类器，把 query 分到固定意图集；线上推理低延迟稳定。
- 优点：毫秒级、确定性高、成本低；缺点：**要标注数据 + 训练管线 + 随业务迭代重训**，新增意图要补数据，口语/长尾鲁棒性依赖训练数据。
- 定位：**意图集固定且量大**的线上高频场景；很多新一代系统拿它当"⑥ 的降本预筛"。**深讲（原理/与⑤对比/生产四件事/选型/大模型形态/话术）见 [档位④深讲](#pa-int-nlu-detail)。**

**⑤ LLM 打分/结构化分类**
- 代表：**ragent 意图树**；LangChain `RouterOutputParser` / Pydantic 结构化输出；LlamaIndex 让 LLM 决定查哪个引擎。
- 做法：把所有候选意图 + 描述/示例拼进 Prompt，LLM 一次性给每个打分或输出 label。
- 优点：口语化/指代全覆盖、能处理复合、阈值可调、**候选可以自带配置**（ragent 叶子挂着 collection/tool/prompt）；缺点：每次多一次 LLM 调用、叶子一多（>30）易串分、效果依赖描述质量。
- 定位：**候选意图多、query 自然语言多样、且候选本身要挂业务参数**时最值（这正是 ragent 的场景）。

**⑥ LLM 路由 + 委托给子执行体（supervisor / handoff）**
- 代表：**PowerAgent IntentAgent**（ADK `transfer_to_agent`）；LangGraph supervisor/`create_agent`；OpenAI Agents SDK / Swarm handoffs；AutoGen GroupChat；Coze/Dify 多 Agent。
- 做法：一个"路由器 Agent"只做决策——LLM 判断场景后把任务**转交**给对应子 Agent 执行（ADK 里 `transfer_to_agent` 是以 function-call 形式暴露的）。可叠加：决策前先走代码显式分支、决策后子 Agent 多步执行。
- 优点：能承载"每个分支需要多步推理 + 独立上下文"的重任务；缺点：调度有额外开销、Agent 间信息传递要设计、有死循环/失控风险（需熔断兜底）。
- 定位：**业务本身就是多场景、每场景要多步执行**的平台（PA 的场景）。

<a id="pa-int-nlu-detail"></a>
### 档位④深讲：分类模型 / NLU（监督意图分类）

> 谱系里夹在 ③（相似度，不用训练）和 ⑤（LLM，靠 Prompt）之间——它把"意图判断"变成一次**训练出来的监督分类**。面试被追到这一档，按下面四层讲。

#### 一句话定位

> 意图集**固定且已知**，就别每次让 LLM 现想——提前把"query → 意图"的关系**学进模型参数**，线上推理只是一次前向计算，毫秒级、可复现、便宜。④ 与 ⑤ 的本质分界：**⑤ 靠上下文"现学现判"（in-context），④ 靠训练时"学死"（in-weights）**。

#### 原理：训练两段 + 推理四步

```text
训练（离线，一次性成本高）
  意图集(固定) ──► 每意图收标注语料(几十~几百条/类起步)
             ├─► 清洗 + 扩充(同义改写/模板/大模型造语料)
             ├─► 基座：微调 encoder(BERT/XLM-R)+分类头，或 Rasa 式 DIET(intent+entity)
             └─► 训练 + 难例挖掘(hard negative) + 类不平衡处理

推理（线上，一次前向）
  query → tokenize → encoder → [CLS]池化 → softmax(全部意图类)
      → argmax(类别) + confidence(概率)
      → confidence ≥ 阈值 → 命中该意图
      → confidence < 阈值  → OOS 拒识 → fallback(默认类/反问/升级 LLM)
```

- **传统 NLU vs 微调 BERT**：Rasa/Dialogflow 是"意图 + 实体"联合抽取的老一套；2023 后自研大多走"微调 encoder 加分类头"，或更进一步**微调 embedding 模型做相似度**（把边界学进向量空间，滑向 ③ 的"训练版"）。谱系不是离散的，④ 与 ③ 两端有渐变。

#### 与 ⑤ LLM 打分分类的本质差异（面试核心对比）

| 维度 | ④ 分类模型/NLU | ⑤ LLM 打分分类（ragent） |
|---|---|---|
| 知识放哪 | **训练进参数** | **Prompt 临时给**（叶子描述+示例） |
| 推理延迟 | 几 ms~几十 ms（encoder 前向） | 几百 ms~秒（一次 LLM 生成） |
| 成本 | 低 1~2 个数量级，CPU 可跑 | 每次 ~2K tokens |
| 确定性 | 100% 可复现 | 靠低温度逼近，非硬保证 |
| 新增意图 | 补数据 + 重训 + 上线（慢） | 改 Prompt/配置立即可用（快） |
| 复合意图 | 弱（单标签匹配，复合要拆层） | 强（"既查 OA 又查保险"可拆） |
| 口语/乱码/长尾 | 取决于训练数据覆盖 | 泛化更好，抗长尾 |
| 幻觉 | 无（判别模型不生成） | 有（可能瞎打分/坏格式） |
| 主要成本 | 数据 + 训练管线 + 维护 | 无训练，每次调用付钱 |
| 最佳场景 | 意图集固定、量大、句式规范、要低延迟 | 意图多变、口语杂、可运营 |

> **面试金句**：④ 便宜在"边际推理"，贵在"意图一变就重训"；⑤ 贵在"每次都现算"，便宜在"意图变化只改配置"。**意图集合越稳定、调用量越大，越该往 ④ 挪；意图越不稳、语义越杂，越该留 ⑤。**

#### 生产落地必须做对四件事（加分项）

1. **OOS 拒识（最易踩的坑）**：分类器会硬给一个类，但 query 可能根本不在意图集里。必须设 confidence 阈值，低于阈值走拒识分支（默认意图 / 反问澄清 / 升级 LLM）——这跟你 ragent"低分退全局检索"、PA"优先级 + 通用兜底"是**同一个工程动作**（可合并概念 K3）。
2. **冷启动与收敛**：每意图几十条高质量起步，不够用 LLM 批量改写造语料；上线后**回灌线上误判样本**做难例挖掘迭代。
3. **类不平衡 + 相似类打架**：意图越细越易混（"查 OA 审批" vs "查保险审批"）。对策：难例负采样、focal loss、必要时**先粗分再细分**两段式。
4. **评测与灰度**：固定 golden set 回归，指标看 precision / recall / **macro-F1**（类不平衡别只看 accuracy）；新增意图走"训练 → 灰度 → 小流量对比 → 全量"。

#### 选型检查表（要不要用 ④）

```
意图集固定、近期不会大改   → 值得（否则重训成本吞收益）
调用量高/延迟敏感/成本敏感 → 值得（vs ⑤ 每轮一次 LLM）
有标注人力/能攒真实样本   → 值得
query 口语天马行空/要复合  → 别硬上 ④，留给 ⑤
意图频繁增减             → 别用 ④
```

#### 大模型时代 ④ 没消失，而是换了形态

- **微调 embedding 而非分类头**：把边界学进向量空间，线上走向量 top-k —— 比裸 semantic router 准，比微调分类头耐新增类（可加类不重训）。
- **small-LM 蒸馏/量化**：拿大模型标注数据蒸馏小模型，兼得 ④ 的速度和接近 ⑤ 的泛化。
- **④ + ⑤ 分层**（2024+ 常见生产架构）：**④ 快速档拦大部分流量，⑤ 只复核模糊/OOS** —— 这其实是 PA"显式分支先拦、LLM 兜底"的同构升级。

#### 回扣两个项目（怎么接"你们为什么不选 / 想怎么补"）

- **ragent 用 ⑤ 不用 ④**：意图叶子要**挂业务参数**（collection/tool/prompt）且随知识库增减，④ 的"加意图 = 加数据重训"在此模型下不可运营；叶子还带 description/examples 依赖 LLM 语义理解。
- **PowerAgent 其实已沾 ④**：第三层"可选小模型工具判定"（`INTENT_ANALYSIS_WITH_TOOL_FLAG` 调 judge 小模型返回确定子 Agent）就是 ④ 的轻量引入。
- **加分回答（优化方向）**：某类意图调用量上去且句式收敛后，可加一条"④ 快速档预筛 + 高分直接放行、低分升级 ⑤"的分层，把大头流量从 LLM 打分里卸下来——把谱系讲活的落地例子。

#### 面试 30 秒话术

> 第四类是监督意图分类——意图集固定就预先训练分类器把"query→意图"学进参数，线上一次前向几毫秒、零幻觉、100% 可复现。优势全在边际推理便宜，代价是意图一变就要补数据、重训、灰度上线，所以适合意图集稳定、量大、延迟成本敏感的场景；意图语义杂、常变、要复合判断时我就用 LLM 打分。生产最关键的是**拒识**——设置信度阈值，低了不硬给类，退回默认或升级 LLM，这个兜底和我 ragent 的"低分退全局检索"、PA 的"优先级+通用兜底"是同一件事。大模型时代它没淘汰，而是变成微调 embedding 或小模型蒸馏，更多作为"快速档预筛 + LLM 复核"的第一层出现。

### 选型决策框架（答"你为啥选这个方案"）

```
意图集固定且窄 / query 固定句式   → ② 规则 / ③ 语义，别上 LLM
意图固定但量大、要低延迟高稳定    → ④ 分类模型/NLU
意图多、口语化、且要挂业务参数     → ⑤ LLM 打分分类（ragent 选型）
场景多、每场景要多步执行、要独立上下文 → ⑥ LLM 路由 + 子 Agent（PA 选型）
```

> **面试一句话**：业界不是"选一个意图识别技术"，是**沿着便宜→灵活的谱系做决策**。两个项目恰好落在谱系两端靠后：ragent 是 ⑤（细粒度、候选挂配置、LLM 打分），PA 是 ⑥ + ② 混合（代码显式分支优先 + LLM 路由委托子 Agent）。真正的成熟工程不是非此即彼，而是**多档串起来**——确定的走便宜档，模糊的才升级到 LLM。

## Q2：ragent 意图树怎么做的（细粒度分类路由）

### 2.1 三个特征一句话

> ① 意图是**数据库配置的树**（`t_intent_node`，DOMAIN→CATEGORY→TOPIC 三层），不是写死的代码；② 识别 = LLM **一次对所有叶子打分**（低温度保证可复现）；③ 分流 = 按叶子 kind（KB/MCP/SYSTEM）+ 阈值决定去**定向检索 / 调工具 / 闲聊短路**。

### 2.2 意图树加载与配置

- 叶子节点带业务属性：`kind`（0=KB 检索 / 1=SYSTEM 闲聊 / 2=MCP 工具）、KB 叶子带 `collection_name` + `top_k`、MCP 叶子带 `mcpToolId`、SYSTEM 叶子可带自定义 `promptTemplate`；非叶子 `description`/`examples` 是喂给 LLM 的描述。（口径以 `IntentKind.java` 为准：KB=0 / SYSTEM=1 / MCP=2）
- 加载链路：Redis 缓存（`ragent:intent:tree`，7 天）→ DB（只查 enabled=1）→ 空则返回空树。**表空 = 意图树空 = 退回全局检索兜底**（见 2.4 的退化）。
- 面试点：这是"**配置驱动的可运营路由**"——新增一个知识库/工具/闲聊场景 = 插一行数据，不动代码。与 PA"Prompt 里写分发规则"形成载体差异。

### 2.3 识别流程与分流

```
subQuestion（Query 改写/拆分后的每个子问题）
   ↓ DefaultIntentClassifier.classifyTargets()
   ↓ LLM 对全部叶子打分 → [{id, score, reason}]，temperature≈0.1 保证可复现
   ↓ 过滤 + 排序
   ├─ KB 意图命中且置信度 ≥ 阈值(0.6) → 意图定向检索（收窄到命中库 collection）
   ├─ KB 意图低分               → 全局作用域检索（全库兜底）
   ├─ MCP 意图命中              → 调 MCP 工具（参数另由 LLM 提取）
   └─ SYSTEM 意图（纯闲聊）     → handleSystemOnly 短路，不检索直接 LLM 答
```

意图识别结果有 **4 个消费点**（不止检索）：① 歧义引导——多意图低分时反问用户"你是想问 A 还是 B"然后短路；② 闲聊短路；③ 检索引擎分流 KB vs MCP；④ 答题 Prompt 增强（LLM 知道"用户问的是哪类 / 我调了哪些工具"）。

### 2.4 与改写的关系 + 退化保护

- **串行且后置**：先 `rewriteQuery()`（术语归一化 + LLM 改写拆分 + 精确实体短路），再 `resolveIntents()` 对每个子问题做意图打分。理由：口语化/指代没消解前做意图识别，命中率掉一大截。**先清后判，顺序不能反**（这是可合并进 PA 话术的概念，见 Q5）。
- 退化保护三级：意图树为空 → 不短路不定向，走全局检索（还能答）；改写 LLM 挂 → 规则拆分兜底；答题 LLM 挂 → 模型 fallback。**每一层的失败都不至于让整次对话挂**。

### 2.5 它的"贵"与"阈值"

每次每子问题多一次 LLM 调用（打分 ~2K tokens）；叶子 >30 个 LLM 容易串分；效果依赖 description/examples 质量与树的合理设计。**评测**靠 `/rag/eval` 返回 `intentLeafIds`，批量对标注集算 Top-1 准确率（详见评测体系文档）。

> 面试讲法一句话：ragent 把意图做成"**可配置的细粒度路由**"——叶子挂了 collection/工具/闲聊三类配置，LLM 低温度打分，阈值决定定向还是全局兜底。代价是每次多一次 LLM 调用，收益是**口语/指代友好 + 能挂业务参数 + 数据驱动可运营**。

<a id="pa-int-q3"></a>
## Q3：PowerAgent IntentAgent 怎么分发（粗粒度场景路由）

### 3.1 一句话

> PA 的"意图识别"不是一个独立模块，而是 **IntentAgent（入口路由器 Agent）的三层决策**：代码显式分支优先 → 模糊场景 LLM 按 Prompt 规则路由 → 可选小模型工具判定；路由结果 = `transfer_to_agent` 把任务交给子 Agent 执行。**IntentAgent 只决策不干活**（"禁止返回业务答案，必须 transfer"写死在 Prompt 里）。

### 3.2 三层识别（对应业界②/⑥/④）

```
用户消息 → IntentAgent
  ① 显式分支（代码，不调 LLM）before_agent_callback
     检查"策略是否已发布/是否在使用"等 100% 确定的业务操作
     → 命中直接返回，跳过 LLM      ← 省一次 LLM 调用，零幻觉
  ② LLM 路由（Prompt 驱动）intent_agent/prompt.py
     System Prompt 写明分发规则 + 决策优先级 + 严禁行为
     → 输出 transfer_to_agent("<sub_agent>")   ← 本质是 function-call 形式
  ③ （可选）工具判定 INTENT_ANALYSIS_WITH_TOOL_FLAG
     调一个小模型/轻量工具返回确定子 Agent → 更快更便宜，灵活度低
```

**② 的 Prompt 长这样**：社交互动→直接简洁回复；元数据操作→`metadata_agent`；策略查看→`strategy_view_agent`（精确匹配词 `查看/显示/列出`）；策略处理→`strategy_agent`（`提取/分析/优化`）；用户数据分析→`direct_analysis_agent`（能提取 chat_id/customer_id）。带**决策优先级**（社交 > 元数据 > 策略查看 > 用户分析 > 通用策略）和**严禁行为**（禁 JSON、禁自己回答业务问题）。

### 3.3 为什么是"路由 Agent"而不是"分类函数"

- ADK 的 `transfer_to_agent` 是**以工具(function-call)暴露的转交能力**，LLM 决策它调哪个子 Agent 后，子 Agent **拿到独立上下文多步执行**（ReAct loop），结果返回主链路。
- 主 Agent 故意**不感知子 Agent 的失败/重试/超时**——子 Agent 内部异常统一返回"请再试一次"，主 Agent Prompt 保持极简，只需知道"分发给谁"。这是分层稳定性（把复杂度下沉到子 Agent）。

### 3.4 为什么没有独立 Rewrite

- PA **没有 Query 重写步骤**：口语/指代消解靠 Agent 循环的 REASONING 阶段隐式完成（长期记忆 + 背景知识注入 Prompt），多问题拆分靠 PlanReAct 的 REASONING。
- 能这么省的前提：**意图粗**（5 个子 Agent 级别，场景固定，LLM 不需要先把问题"标准化"也能分对）。意图越细（像 ragent 几十个叶子），越需要独立改写前置。

### 3.5 它的已知短板（面试诚实项，来源 PA 自评）

- 意图路由**粗粒度**：只能到 5 个子 Agent，区分不了"OA 审批 vs 保险审批"这种细粒度 FAQ——因为定位是多业务 Agent 平台而非 FAQ 系统，知识库路由在 WorkFlow 节点配置时已手动指定。
- 改进方向（PA 文档自列）：参考 ragent 意图树——在 datasetSearchNode 前加一层意图分类，动态传 `knowledgeIds`。
- LLM 路由依赖 LLM 判断（有幻觉风险），靠"严格限制只能转交"缓解；规则关键词多时 Prompt 维护成本上升。

> 面试讲法一句话：PA 的意图识别是入口 **IntentAgent 的三层决策**——确定的场景用代码分支直接命中（省 LLM、零幻觉），模糊场景让 LLM 按 Prompt 规则 `transfer_to_agent` 到子 Agent 深度执行。它是"**任务分发级的路由**"，粗粒度、不配独立 Rewrite，换来的是多场景多步执行的 Agent 能力。

<a id="pa-int-q4"></a>
## Q4：两套横向对比——粒度 / 载体 / 下游 / 成本

> 这是"两个项目都是你做的，它们意图识别有什么不同"的标准答案底稿（素材对齐 PowerAgent 文档 RAG 管线对比章）。

| 维度 | ragent 意图树 | PowerAgent IntentAgent |
|---|---|---|
| 定位 | FAQ 知识问答的**细粒度知识库路由** | 多业务 Agent 平台的**粗粒度场景路由** |
| 判得有多细 | 叶子意图（可到"查 OA 审批流程 vs 查保险审批流程"） | 到 5 个子 Agent（"查看策略 vs 分析策略 vs 跑数据"） |
| 载体 | DB 三层意图树（数据驱动，插行即加意图） | 代码分支 + Prompt 规则（改代码/Prompt） |
| 识别机制 | LLM 对所有叶子一次性打分（低温度） | 代码显式分支 → LLM 路由（transfer_to_agent）→ 可选小模型 |
| 下游动作 | KB 定向检索 / MCP 工具 / 闲聊短路 | 转交子 Agent 多步执行 |
| 决策成本 | **每子问题一次 LLM 打分** | 仅入口 IntentAgent 一次 LLM 路由（显式分支命中则零次） |
| Rewrite | 独立步骤且前置（先清后判） | 无独立步骤，REASONING 隐式完成 |
| 短路能力 | 闲聊 SYSTEM / 歧义引导 / MCP 都有显式分流 | 社交直接回复（Prompt 指令） |
| 核心优势 | 细粒度定向 + 候选挂业务参数 + 可运营 | 每个意图 = 一个能深度执行的 Agent |
| 核心代价 | 意图越多打分越易串、每轮多一次 LLM | 路由粗，做不了细粒度 FAQ 定向 |
| 互相可借鉴 | → PA 可在检索节点前加意图分类补细粒度 | ragent 的细粒度就是 PA 自评的改进方向 |

### 为什么会有这种差异（答"为什么这么设计"）

```
ragent：FAQ 知识问答，一次问一个知识点 → 需要精确"查到对的库/段落"
        → 意图必须细，细就需要先把口语/术语改写清楚，于是独立 Rewrite + 叶子打分
PA   ：多业务场景 Agent，一句"帮我分析这个策略"要拉数+分析+生成+验证
        → 意图不必细，但要能承载多步执行 → 路由器 + 子 Agent，Rewrite 交给循环隐式做
```

> 本质一句话：**意图粒度必须匹配下游动作的复杂度**——下游是"检索一段"就要细到库/主题，下游是"执行一个任务"就粗到场景/子 Agent。意图设计永远跟着下游走，不是技术炫技。

## Q5：可合并讲的概念（一次讲清，别讲两遍）

下面这些**概念**两套系统一致，面试主答案讲一遍就够，被追问实现再点名是哪个项目：

| # | 可合并概念 | 讲一遍的话术 | ragent 落地 | PA 落地 |
|---|---|---|---|---|
| K1 | 意图识别 = 路由器，不是检索 | "本质是'用户说了什么→谁处理'的决策，决策对象是 KB/工具/子Agent/闲聊" | 叶子 kind 分流三类 | transfer_to_agent 到子 Agent |
| K2 | 便宜的确定分支永远放最前（省 LLM） | "100% 确定的场景先用规则/代码命中，模糊才升级 LLM——成本、幻觉双降" | Query 精确实体短路（正则） | `before_agent_callback` 显式分支 |
| K3 | 兜底不能断 | "识别失败/配置空时要能退到可用路径，别让对话死掉" | 意图树空 → 全局检索；低分 → 全局 | 决策优先级 + 通用策略兜底 |
| K4 | 先清后判（Rewrite 在意图前） | "口语/指代不清时先做意图一定分不准；先消解改写、后判断意图" | 独立 `rewriteQuery()` 前置 | REASONING 隐式消解（意图粗故够用） |
| K5 | 意图粒度跟下游走 | "下游是检索→意图细到库；下游是执行→意图粗到场景/子 Agent" | 细粒度叶子 | 粗粒度子 Agent |
| K6 | 决策要有可运营性/可评测 | "意图要能加要能测，否则没人敢动" | DB 树可插行 + `/rag/eval` Top-1 准确率 | Prompt/代码规则 + 显式分支单测覆盖 |

> **不可合并（必须分项目讲）**：两套的**载体与下游**——ragent 是"数据驱动的细粒度分类路由（LLM 打分 + 阈值定向检索）"，PA 是"Agent 入口的三层任务分发（代码 + LLM 路由 + 子 Agent 深度执行）"。这两句是各自的身份标识，合并讲等于抹掉差异、露馅。规则：**K1~K6 概念层一次讲清，载体/粒度/下游实现层分项目讲**。

## Q6：面试速记表 + 三档最优回答 + 追问预案

### 6.1 速记表

| 一句话 | 内容 |
|---|---|
| 本质 | 意图识别 = "谁处理"的路由决策，不是检索 |
| 业界谱系 | ① 无识别 ② 规则 ③ 语义(embedding) ④ 分类模型 ⑤ LLM 打分分类 ⑥ LLM 路由+子 Agent |
| ragent 座标 | ②（精确实体短路）+ ⑤（LLM 叶子打分），**细粒度知识库路由** |
| PA 座标 | ②（显式分支）+ ⑥（transfer_to_agent），**粗粒度任务分发路由** |
| 载体差异 | DB 三层意图树（数据驱动）vs 代码+Prompt 规则 |
| 下游差异 | KB/MCP/闲聊 分流 vs 子 Agent 多步执行 |
| Rewrite | 独立前置（先清后判）vs 无独立步骤（REASONING 隐式） |
| 设计公理 | 意图粒度跟下游动作走：检索→细，执行→粗 |

### 6.2 最优回答——三档场景

**档 A：只讲 ragent（被问"你的意图识别怎么做的 / 和直接全库检索比好在哪"）**

> 我的系统是 FAQ 知识问答，所以意图识别做成"**可配置的细粒度路由**"：DB 里配一棵三层意图树，叶子节点按 kind 分三类——KB 叶子挂 collection（定向检索）、MCP 叶子挂工具、SYSTEM 叶子走闲聊短路。识别时 LLM 一次性对所有叶子打分（低温度保证可复现），按分数分流：KB 高分且置信度够 → 定向到命中库检索；分低 → 退回全局检索兜底；命中工具 → 调 MCP；纯闲聊 → 短路不检索直接答。它放 Query 改写之后——先做术语归一化和指代消解，再做意图才分得准。为什么不用语义路由（embedding 相似度）？因为它对"ADK 和 React 区别"这种边界模糊、两个类分接近的 query 会误吸，而 LLM 打分能看描述+示例做语义判断，还顺带能处理复合意图。代价是每次多一次 LLM 调用，叶子超 30 个会串分——所以树要设计得合理，评测靠 /rag/eval 对标注集算意图 Top-1 准确率。

**档 B：只讲 PowerAgent（被问"你的意图识别/分发怎么做的"）**

> 我这边是多业务场景的 Agent 平台，意图识别是入口 **IntentAgent 的三层任务分发**。第一层代码显式分支——像"检查策略是否已发布"这种 100% 确定的业务操作，before_agent_callback 直接命中返回，不调 LLM，省成本也零幻觉。第二层 LLM 路由——模糊场景让 LLM 按 System Prompt 的分发规则（配精确匹配词、决策优先级、严禁行为）输出 `transfer_to_agent`，把任务交给对应子 Agent。关键设计是 **IntentAgent 只决策不干活**，业务答案一律不允许它自己生成，必须转交；子 Agent 拿到独立上下文做 ReAct 多步执行，失败统一返回兜底消息，主 Agent 感知不到复杂度。第三层可选小模型工具判定。我没做独立 Query 重写，因为意图是粗粒度的（到子 Agent 级），口语/指代靠 Agent 循环的 REASONING 阶段隐式消解就够了。这层设计也有已知短板——路由粗，做不了"OA vs 保险审批"这种细粒度定向，这是我们改进方向。

**档 C：两套都被问（"这两个项目意图识别有什么不同 / 你怎么选型"）**

> 两套我都做过，本质是同一个问题——"用户说了什么该谁处理"——但粒度完全不同，因为下游不同。ragent 是 FAQ 知识问答，一次问一个知识点，需要精确命中"对的库"，所以意图要做**细**：DB 配三层意图树，LLM 对所有叶子打分，KB/MCP/SYSTEM 分流，还配了独立 Query 改写前置。PowerAgent 是多业务 Agent 平台，一句"分析这个策略"要拉数、分析、生成、验证，所以意图不必细到知识库，但要能承载多步执行：入口 IntentAgent 三层分发（代码显式分支优先省 LLM，模糊场景 transfer_to_agent 到子 Agent），Rewrite 交给循环隐式做。业界看这就是一张谱系——无识别→规则→语义路由→分类模型→LLM 打分→LLM 路由+子 Agent，两个项目落在不同档。**选型的公理是意图粒度跟着下游动作走：下游是检索就细到库/主题，下游是执行就粗到场景/子 Agent。** 而且真正成熟的工程不是只选一档——两个项目都是先把 100% 确定的用代码命中（ragent 的精确实体短路、PA 的显式分支），模糊的才升级到 LLM。

### 6.3 追问预案表

| 追问 | 怎么接 | 指向 |
|---|---|---|
| 为什么不用语义路由 / embedding 分类？ | 边界模糊 query 会误吸到语义近但错的类，且判不了复合意图；LLM 打分能看描述+示例。语义路由适合类间距离大的场景 | [Q1 ③⑤](#pa-int-q1) |

| IntentAgent 用 LLM 不怕幻觉/乱转交？ | 双重约束：显式分支先拦确定场景；Prompt 写死"只准转交不准自己答"；子 Agent 失败统一兜底消息不外溢 | [Q3 3.2-3.3](#pa-int-q3) |

| 意图识别怎么评测 / 保证效果？ | ragent：/rag/eval 批量对标注集算意图 Top-1 准确率 + 检索指标；PA：显式分支单测覆盖 + Prompt 规则 golden case 回归。低温度保证可复现便于回归 | [Q2 2.5](#pa-int-q2) |

<a id="pa-int-q7"></a>
## Q7：客服 chatbot——意图识别够不够用？槽位层现状 + tool_call 判定

> 意图总纲的落地应用篇。假设用现有体系做一个 task-oriented 客服 bot（查物流/改单），回答三件事：意图识别够不够、实体抽取做到哪、槽位齐了要不要 tool_call。

### 7.1 结论：意图层够，槽位层缺

客服 bot 分两类——**FAQ 型**（问知识，检索直接答）和 **task 型**（查物流/改单，要带参数调后端）。对 task 型，NLU 是**两件套**：意图分类 + 槽位填充，且后面还要动作执行。现有意图识别把**意图层**做得很足，但**槽位层**没当一等公民建模：

| 层 | 回答的问题 | 例子 | 现有覆盖 |
|---|---|---|---|
| 意图层 | 用户要哪个流程 | 动作=查物流 | ✅ 超配（ragent ⑤ 打分 / PA ⑥ 分发） |
| 槽位层 | 执行流程要哪些参数、值是什么 | 产品=MacBook、时间=上个月 | ⚠️ 只有"LLM 顺带填参" |

> 一句话：意图识别答"用户想干嘛"，槽位层答"干这事要哪些具体值"——后者才是客服 bot 的差距所在（前者本总纲 Q0~Q6 已覆盖）。

### 7.2 项目里"实体抽取"做到哪一步（三档）

| 档位 | 做了什么 | 落在哪 | 缺口 |
|---|---|---|---|
| ✅ 有 | 按工具 schema 的 LLM 参数抽取 | ragent `McpParameterExtractor`（每 MCP 节点可配 `param_prompt_template` 定制提取）；PA `ParamExtractAgent`（抽策略/执行参数后交 execute agent） | 能填出 JSON，但不校验、无缺失追问 |
| ◐ 半有 | 术语归一化；实体"存在性"识别 | ragent `QueryTermMappingService`（同义词→标准词，"平安保司"→"平安保险公司"）；`ExactEntityDetector`（4 类正则判**有无**实体，不抽值） | 只覆盖维护过的别名；归一到标准品无通用消歧 |
| ✗ 没有 | 真正的槽位建模 | — | schema 必填/可选、**相对时间归一**（"上个月"→区间）、缺槽反问、跨轮槽位累积（DST）都缺 |

对照你给的槽位例子：

| 槽位 | 现状 |
|---|---|
| 动作=查物流 | ✅ 意图层命中即定（MCP 叶子已绑 `mcpToolId` / PA 已 transfer 到对应 agent） |
| 产品=MacBook | ⚠️ LLM 能抽出；归一到商品标准品只靠术语表，没维护就归不了 |
| 时间=上个月 | ❌ `ExactEntityDetector` 只认显式日期（`2024-06-30`/`2024年6月`）；相对时间无 resolver 转 [start,end] |

> **金句**："LLM 填参" ≠ "实体抽取"——前者"能填就填、填不上拉倒"；后者要求 **schema 强约束**（必填/可选/默认/合法性/归一规则）+ 缺失反问闭环。

### 7.3 补法：schema 驱动的槽位层（复用现有资产，不推倒重来）

在意图层后加一层，**槽位 schema 直接复用工具的参数 JSON Schema**（schema 只有一份，意图树/槽位/执行器三方对表）：

```
意图识别(命中"查物流")
  → 挂该工具参数 schema = 槽位定义
       {orderNo: 必填/正则, product?: 归一到商品词典, time?: TimeResolver}
  → 两段式抽取：
       · 确定型(订单号/型号/显式日期) → 规则/resolver（复用 ExactEntityDetector + 补 TimeResolver 算相对时间区间）
       · 自由文本槽              → LLM 抽取（复用 McpParameterExtractor 的 schema 填参）
  → schema 校验：缺必填 → 澄清反问一次补一槽（复用 handleGuidance 的反问链路）
  → 槽位齐   → 确定性 execute（见 7.4）
  → 未齐槽位 → 暂存短期记忆，下轮 rewrite 带历史续填
```

优势：这是 Q1 谱系"④ + ⑤ 分层"思想的翻版——**确定型实体走便宜的规则/resolver，自由文本才上 LLM，schema 校验兜底 + 反问闭环**。

### 7.4 Tool 能力层 vs tool_call 驱动层（槽位齐了要不要 tool_call）

"调物流 API"当然封装成 tool，但"封装成 tool"和"走 LLM tool_call"是两层，别混：

| | 封装成 tool（能力层） | tool_call（驱动/触发层） |
|---|---|---|
| 是什么 | 把 API 注册为 `queryLogistics`：名字 + 参数 schema + 执行函数 | LLM 输出的结构化动作 `tool_call(name, args)` |
| 回答的问题 | 系统"能调什么" | 这次"由谁来调、参数谁给" |
| 在不在 | 两种范式**都必有**，共用同一注册表 | 仅"让 LLM 决策"时才出现 |

**结论：tool 必须有，LLM tool_call 可以不要。** 固定客服流程里，意图已把 tool 定死（映射到 `mcpToolId` / 子 Agent）、槽位已把参数校验齐——调度器**直接**按 name 查同一注册表执行即可，不需要 LLM 重新生成一次调用。两条路径的执行器代码一模一样，区别只在"name + args 是谁定的"。

**仍然需要 LLM tool_call 的开放点（4 种）**：① 一个槽位值会路由到多个工具；② 槽位要再加工成 SQL/检索词等生成型入参；③ 走 Agent/ReAct 的不确定子步骤（如 PA 策略分析）；④ 槽位 schema 兜不住的自由文本。其余一律确定性收尾——省一次 LLM、避免参数被模型改写、可审计可 Trace。

### 7.5 面试话术（30 秒）

> 我把意图识别拆两层看：意图层（用户要哪个流程）做客服 bot 一定够用，我这边细粒度（ragent 树打分）和粗粒度（PA IntentAgent 分发）都有成熟方案；真正的差距在槽位层（执行流程要哪些参数）。项目里实体抽取现在是"LLM 按工具 schema 顺带填参"加"术语表归一"，不是真正的槽位模型——缺必填/可选约束、缺相对时间归一（"上个月"这种不会自动转区间）、缺缺槽反问和跨轮续填。补法是意图层后面加 schema 驱动槽位：槽位 schema 直接复用工具参数 schema，确定型实体走规则/resolver、自由文本才调 LLM，校验缺了反问补槽。至于槽位齐了要不要 tool_call——tool 一定封装（能力层所有范式共用），但 LLM tool_call 不必走：意图已定死工具、槽位已校验参数，调度器直接执行同一个 tool；只有槽位值会路由到多个工具、或参数需要再生成时，才让 LLM 补一发 function call。
